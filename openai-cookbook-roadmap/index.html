理解 OpenAI API 体系

🔹 API 有哪几种"口味"？

API 类型定位适用场景
Chat Completions最简单的 text-in text-out基础聊天、单次问答
Responses API统一接口：文字+工具+图片+音频+结构化新项目首选
Realtime API低延迟语音会话（WebSocket）语音助手、实时翻译
Agents SDKAgent 框架封装多工具编排、自主代理
Assistants API（旧）带状态管理的对话已逐渐被 Agents SDK 取代
💡 注意：Cookbook 里老一点示例用 Chat Completions，新的基本都在用 Responses API 了。

🧱 核心"积木"概念

① Messages（消息结构）

每次请求本质上是发一个消息列表给模型，有四种角色：

  • system — 设定 AI 的角色和行为边界（如"你是一个专业的客服"）
  • user — 用户的输入
  • assistant — 模型的回复
  • tool — 工具调用返回的结果
📌 要点

消息列表就是模型的"记忆"，越长越贵。如何管理上下文长度是一门核心学问。

② Models（模型家族）

当前主要模型分三大类：

GPT 系列（通用）
直觉派——快但可能出错
GPT-4o / 4o-mini — 性价比主力，支持多模态
GPT-5 系列 — 最新最强，Agent 能力大幅提升
GPT-4.1 — 之前的版本
o 系列（推理型）
推理派——慢但准确，适合数学/逻辑/规划
o1 / o3 / o4-mini — 会"思考"的模型，内部推理消耗更多 token
gpt-oss 系列（开源权重）
OpenAI 开源的模型权重，可本地部署
📌 要点

选模型就是在速度、成本、质量之间做取舍。GPT 系列适合通用场景，o 系列适合复杂推理。

③ Tools（工具调用）

这是当前 AI 应用最核心的概念——模型不直接执行代码，而是输出工具调用请求，由开发者执行并返回结果：

用户提问 → 模型决定是否用工具 → 调用工具 → 工具返回结果 → 模型整合回答

Cookbook 里大量示例（Function Calling、Web Search、File Search）都是这个机制的不同应用。

④ Structured Outputs（结构化输出）

以前需要自己解析模型返回的文本；现在你定义 JSON Schema，模型保证格式完全匹配：

你定义：{ "姓名": string, "年龄": number } ↓ 模型返回：{ "姓名": "张三", "年龄": 28 } ← 100% 符合格式

⑤ Streaming（流式输出）

模型不是等想完才回答，而是一个 token 一个 token 往外吐。流式输出实现"打字效果"，用户体验更好。

🔄 整个请求的生命周期

你的应用 ↓ 准备：消息列表 + 模型选择 + 工具定义 OpenAI API ↓ 模型处理：理解上下文 → 推理 → （可能调用工具）→ 生成 ↓ 返回结果（流式或一次返回） ↓ 你的应用处理输出

📝 一句话总结第一阶段

OpenAI API 本质就是把消息发给模型，模型决定要不要用工具，然后把回答返回给你。所有高级功能（RAG、Agent、多模态）都是在这个简单模型上叠加的。
