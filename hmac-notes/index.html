01

是什么？

HMAC（Hash-based Message Authentication Code，基于哈希的消息认证码）—— 一种用哈希函数 + 密钥来验证消息完整性和真实性的技术。

一句话

HMAC = 带密钥的哈希。实际实现用两次哈希 + 密钥填充，防止长度扩展攻击。

02

为什么需要它？

场景：你在浏览器发请求"转账 100 元"，中间人篡改成"转账 10000 元"。怎么发现？

普通哈希（MD5/SHA-256）的缺陷：能发现篡改，但攻击者可以重新计算哈希，伪造出合法的校验值 —— 因为哈希计算不需要密钥，任何人都能算。

HMAC 的解决思路：把密钥混进哈希计算。只有持有密钥的人才能算出正确的认证码，攻击者没有密钥，篡改后算不出匹配的 MAC → 被识破。

普通哈希 (SHA-256)HMAC
是否需要密钥❌ 不需要✅ 需要
防篡改⚠️ 能发现，但攻击者可重算✅ 攻击者无密钥无法伪造
防伪造❌✅
公式H(消息)H(密钥⊕pad + H(密钥⊕pad + 消息))
03

工作流程

发送方：消息 + 密钥 → HMAC 算法 → 认证码 (MAC) → 发送 [消息 + MAC]
接收方：收到消息 → 用手中密钥重算 HMAC → 比对 MAC → 一致 = 未被篡改 + 来自持有密钥的一方
04

算法原理：为什么不能简单哈希？

朴素方案的问题：长度扩展攻击

如果 MAC = SHA256(密钥 + 消息)，攻击者虽然不知道密钥，却能基于已得到的哈希值，凭空构造出「密钥+消息+追加内容」的合法 MAC —— 这叫长度扩展攻击。

所以 HMAC 规范（RFC 2104）设计成了两次哈希 + 两个填充：

# HMAC 计算过程
步骤1: 密钥填充到块大小(64字节)，记为 K'
步骤2: inner = SHA256( (K' ⊕ ipad) + 消息 )    # ipad = 0x36 重复填充
步骤3: outer = SHA256( (K' ⊕ opad) + inner )  # opad = 0x5C 重复填充
结果:   HMAC = outer
📌 要点

两个填充值（0x36 / 0x5C）故意取不同的常数，把密钥"揉"进两个不同的哈希上下文。第二次哈希把第一次结果再包一层，长度扩展攻击失效。

HMAC 不是"哈希前加个密钥"这么简单，而是用密钥派生的两个掩码分别参与两次哈希，最终输出跟密钥和消息都强绑定。

05

HMAC 的四种属性

属性含义
确定性相同输入 → 相同输出（所以能比对）
密钥依赖输出不可预测，无密钥算不出来
篡改敏感消息改一个比特，MAC 完全不同
不可伪造计算上不可逆，无法反推密钥
06

HMAC 防不住什么？

① 密钥泄露

HMAC 的所有安全都押在密钥上。密钥丢了 = 保险箱钥匙被复制，HMAC 形同虚设。

② 重放攻击（Replay）

HMAC 能证明消息没被改，但证明不了消息是新的：

攻击者窃听: [转账请求 + 合法MAC] → 原封不动再发一次！

银行验证：MAC 正确 ✅ 又执行了一次转账。

防御手段（在消息里加时间戳或一次性随机数 Nonce）：

  • 时间戳：接收方检查时间差，超过阈值直接拒绝
  • Nonce：每个请求带唯一随机数，接收方记录用过的不再接受
  • 两者结合最稳（OAuth、AWS 签名都是这么做的）

③ 中间人改写协议逻辑

HMAC 只管消息本身，不管"这个消息该不该发"（权限、频率等）。

07

真实应用：API 签名

HMAC 最经典的生产场景：

# 客户端
1. 构造请求参数（方法 + 路径 + 时间戳 + 消息体）
2. 按规则拼接成规范字符串
3. HMAC-SHA256(密钥, 规范字符串) → 签名
4. 请求头带上: Authorization: HMAC ***
# 服务器
1. 取出请求参数，按相同规则拼接
2. 用数据库里存的该用户密钥重新计算 HMAC
3. 比对两个签名 → 一致才放行
4. 检查时间戳 → 太旧就拒绝（防重放）

为什么这样设计？

  • 密钥在两端各存一份，永远不随请求传输（这是和"校验值一起传"的 MD5 的根本区别）
  • 时间戳防重放
  • 请求内容参与签名 → 参数被篡改，签名立刻对不上
📌 实例

云厂商的 API 签名（AWS SigV4、腾讯云 TC3-HMAC-SHA256）本质都是这个模式，只是拼接规则和哈希细节更复杂。

08

HMAC vs 数字签名

HMAC数字签名（RSA/ECDSA）
密钥体系对称（同一个密钥）非对称（私钥签、公钥验）
能证明"谁发的"？⚠️ 只能证明"持有密钥的一方"✅ 能证明到具体的人/机构
适合场景自己系统内部、API 调用方是你认识的人对外发布、需要追责、多方协作
性能快慢

场景判断：微信支付回调验签用 HMAC 就够（双方共知密钥）；但 HTTPS 证书、软件发布签名必须用数字签名（全世界都要验证，私钥不能分发）。

📝 总结

HMAC 安全 = 密钥保密 ✅ + 消息防篡改 ✅ + 防重放(时间戳/Nonce) ✅

HMAC 是"共享秘密"时代的完美工具，但它替你做不了三件事：分发密钥、证明身份归属、抵御重放。真实系统里这三件事分别由密钥管理系统、数字签名、时间戳机制来补。
